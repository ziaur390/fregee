# Architecture

Why the pieces are arranged this way. The README covers *what* each part does;
this document covers the decisions that are not obvious from the code.

---

## 1. One set of weights, three runtimes

`model.pt` is trained once. `export.py` derives TorchScript, ONNX fp32 and ONNX
int8 from it. Nothing else produces a servable artefact.

This is the constraint that makes the benchmark an experiment rather than an
advertisement. If each runtime had its own training run, a latency difference
could be a difference in the model, the seed, or the data split, and no amount of
statistics would separate them. `export.py` enforces the property by asserting
that all three agree on labels across the test split, and it **fails the build**
rather than warning — a silently broken export produces a full page of
confident, meaningless numbers.

The cost: int8 quantisation is measured against a model that was trained in fp32
without quantisation-aware training. That understates what int8 can do, and it is
the honest comparison for "I have a trained model, should I quantise it?"

---

## 2. `inproc` and `http` are separate measurement modes

An HTTP round trip includes JSON parsing, pydantic validation, ASGI overhead and
connection reuse. `inproc` calls `registry.load(...).predict(...)` directly and
includes none of it.

Both are measured because the difference between them is diagnostic:

- If a runtime is slow in **both**, the runtime is slow.
- If it is slow only in **http**, the API is slow — maybe it is being asked for
  larger batches, or the validation path is doing more work.

Reporting only one mode makes that inference impossible. A benchmark that
measures only HTTP and concludes "ONNX is faster" has not established *why*.

---

## 3. Constant call count, not constant sample count

`configs/bench.yaml` fixes `calls_per_repeat: 70`, not a sample budget.

Two questions need different things held fixed:

- **Latency** is a per-call distribution. Fixing the sample count would give
  batch-1 cells 70x the observations of batch-64 cells, and the p99 would then be
  estimated from different-sized samples depending on batch size — an invalid
  comparison.
- **Throughput** is a rate. It normalises correctly even though one batch-64 call
  carries 64x the samples of a batch-1 call.

70 × 3 repeats = 210 observations per cell, which was **derived** rather than
chosen: a p95 needs 200 observations for 10 samples to land in its tail
(`min_tail_observations: 10`). The p99 needs 1,000 and is therefore reported as
unpowered instead of quietly printed.

---

## 4. Paired bootstrap for comparisons

`bootstrap_ratio_ci` resamples **index positions** and applies the same index to
both sequences. Two measurements from the same cell share a machine, a thermal
state and a load level; treating them as independent inflates the interval enough
to turn a real 1.1x difference into "no measurable difference".

There is a test for this (`test_paired_bootstrap_is_narrower_than_independent`)
because it is the kind of correctness property that silently regresses.

---

## 5. Persistence is off the critical path — and off the benchmark

`record_request` runs as a FastAPI background task. Two consequences:

- Database latency is not charged to the caller, so the p99 in the benchmark is
  inference latency and not storage latency.
- The benchmark's own server sets `MLSERVE_REQUEST_LOG=0`. Persistence is a
  separate subsystem, and leaving it on would let 64 sequential inserts per
  batch-64 request show up in the *next* request's latency, blending two things
  that should be measured separately.

`request_id` is generated by the caller and is the primary key. That is what makes
restores idempotent: re-inserting a restored row conflicts and is skipped. Without
it, the restore drill would inflate the very row count it is verifying.

---

## 6. Pruning lives in the drift job, not the write path

An earlier version counted rows after every insert to enforce a row cap. That made
writes quadratic in table size, and it is why the first full HTTP benchmark stalled
at around twelve minutes instead of finishing in about one.

`db.prune` is now called by the drift cron job. It is maintenance, and it does not
belong in the path a user is waiting on. The test suite asserts the write path does
not call it.

---

## 7. Readiness is not liveness

`/healthz` reports only that the process is alive and never touches the model or
the database. `/readyz` fails when the default runtime cannot be loaded.

Wiring the model check into `/healthz` is the classic mistake: a bad deploy then
makes the orchestrator kill a process that was healthy, and the restart storm
hides the real cause. The tests assert both halves — readiness returns 503 when the
model is missing, and **liveness still returns 200**.

---

## 8. PSI decides, KS corroborates

Argued in full at the top of `configs/drift.yaml`. The short form:

| | PSI | KS |
|---|---|---|
| Kind | magnitude | hypothesis test |
| Sample-size dependent | no | yes — significance grows with n |
| Output | one number with conventional bands | statistic + p-value |
| Across 64 features | 64 comparable numbers | 64 tests ≈ 3 false positives per run |

A detector that fires on noise gets muted, and a muted detector is worse than no
detector. So PSI drives the alert and KS is recorded as supporting evidence: when
PSI says a feature moved and KS agrees, the shift is real rather than a binning
artefact.

**Zero-variance features are excluded.** Three of the 64 digit pixels are constant
background in every training image. Such a feature has no reference distribution,
so its PSI is 0 by construction no matter what production sends. Including it would
dilute the mean and inflate the denominator of `fraction_watched`. They are counted
and reported instead.

---

## 9. The reference is quantile-binned, and that claim has a caveat

Equal-width bins over `[0, 1]` would put ~90% of every pixel feature into the first
bin, because most pixels are background — a shift inside that bin would be
invisible. Quantile edges avoid that in principle.

In practice, heavy ties mean many quantiles return the same value, so several bins
end up zero-width and empty. That turns out to **help**: an empty reference bin has
proportion zero, so production traffic landing there produces a large PSI
contribution. The detector becomes more sensitive to values the model never saw,
which is the failure it exists to catch. The epsilon in the PSI keeps the logarithm
finite.

There is deliberately **no** `np.unique` on the interior edges. It looks like it
would help, but deduplicating gives features *different numbers of edges*, which
breaks the stacked array and makes the reference shape data-dependent.

---

## 10. Verified restore, not just a backup

`ops/backup.py` writes an archive, then `verify_restore` extracts it, restores the
database into a **scratch** database, and asserts checksum and row-count parity
against the manifest. Any mismatch raises.

The systemd unit runs `create` and `verify` in the same service. Putting
verification in a separate timer means it can be disabled without anyone noticing
that the backup is now unproven.

Half the backup test suite exercises the failure path — corrupted database,
deleted database, missing manifest, tampered artefact, doctored row count. A
verifier that has only ever been observed to pass has not been tested.

SQLite is copied with `sqlite3.Connection.backup`, not `shutil.copy`. A file copy
of a live SQLite database can capture a torn write: the page cache and any
in-flight transaction are not in the file yet, so the copy is internally
inconsistent while looking perfectly valid.

---

## 11. Provisioning and configuration are separate

`terraform/` creates the host and prints the exact `ansible-playbook` command to
run next. It does not invoke Ansible.

The split matters because the two have different lifetimes. Re-running
configuration must not risk recreating the machine. Merging them into one
`terraform apply` that shells out to Ansible is convenient once and dangerous
every time after.

The Ansible playbook is written to be idempotent — a second run must report zero
changed tasks. That is the test, because a provisioning script that cannot be
re-run cannot fix a partial failure.

---

## 12. Everything must run at zero cost

No managed monitoring, no hosted database, no paging service, no paid runner.

This is not only a budget constraint. A stack that needs a credit card to
demonstrate is a stack nobody can verify, and a claim nobody can verify is worth
much less. Concretely:

- Alertmanager routes to a local webhook receiver, so the alerting path can be
  *observed* firing rather than read in a config file.
- The model trains on CPU in seconds, so CI can run the full pipeline.
- The VM path targets Multipass locally and Oracle Cloud Always Free remotely.
- `tasks.py` is pure standard library, so nothing needs installing to run the
  project.
