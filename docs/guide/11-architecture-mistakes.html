The three layers, and why they are separated

LayerContainsWhy it is separate
Knowledge The model, the reference distribution Expensive to produce, so it is built once and stored. Everything else consumes it read-only.
Service The API, the runtimes Fast, always running, answers users. Replaceable at any time without losing the model.
Governance Monitoring, drift, backup, tests, CI Not on the user path at all. These exist so that the other two can be trusted — and they can fail without breaking anything the user sees.

That third layer is the part most projects skip, and it is the entire point of this one. A model plus an API is a demo. A model plus an API plus monitoring, drift detection, verified backups and automated checks is a service.

The one-line summary

If you remember one thing

A machine-learning project is 10% model and 90% the engineering that makes the model trustworthy. This repository is deliberately built so that the 90% is visible — the parts you cannot photograph, demo, or put on a slide, and that determine whether the thing actually works.

PART 19

Twenty-one mistakes, and what each one teaches

This is the most valuable part of this document. Not because the mistakes are interesting in themselves, but because every one of them is a mistake you will otherwise make yourself — and recognising the pattern is what transfers.

These are all real, all found during the work, and all fixed. Some were caught by tests; several were caught only because something looked slightly odd and was investigated properly.

Category 1 — The ones where everything looked fine

#What went wrongWhy it was invisibleThe lesson
1 The benchmark was not reproducible. Two runs of the identical command timed different inputs. The difference looked exactly like ordinary timing noise — which is precisely what a benchmark expects to see. A bug that mimics expected noise is the hardest kind to find, because the output never looks wrong.
2 Python's built-in hashing was used for seeding. Python deliberately randomises it per process. Nobody suspects the language itself. It is a documented feature, not a bug. Use an explicitly stable function (like SHA-256) for anything that must be identical across runs. Never assume "the same input gives the same output" unless you have checked.
3 The container's Python was never tested. Deployment moved to 3.14; the checks stopped at 3.13. Every single check passed. All green. Completely misleading. A check that passes for the wrong reason is worse than no check. Ask: what would make this go red? For a version matrix, the answer must include the version you actually deploy.
4 The image size in the documentation was wrong — stated as 484 MB when it was 2.24 GB. It was recorded early and never re-measured. Nobody questions a number they wrote themselves. Numbers in documentation go stale. Re-measure before publishing, especially numbers that flatter.
5 Drift detection would have been blind to a broken detector. "No drift" and "nothing measured" looked identical. Both show as "no drift". A dashboard cannot tell them apart — not because the dashboard is bad, but because the information was never recorded. Always ask of any monitoring signal: what does this look like when the thing producing it is dead?

Category 2 — The ones that only appear in a different environment

#What went wrongWhy it was invisibleThe lesson
6 Permission denied in the container only. The results folder resolved to a location owned by the administrator. On a developer's machine that folder is writable. It always worked locally. "Works on my machine" is usually not carelessness — it is a genuinely different environment. Defaults that resolve relative to a file's location change meaning when the file moves.
7 A storage folder was created owned by the wrong user, so the drift job could not write its output. The folder was created automatically by the container system, not by our code, so it was not obvious it needed attention. Create your own directories explicitly, with the right owner, before something else creates them wrongly. Then verify writability during the build so it fails early and loudly.
8 Four of nine containers reported unhealthy while working perfectly. Starting the project appeared to hang forever. The health check was defined once, in the shared image — but only one of the five jobs using that image actually serves web traffic. Put a check next to the thing it checks. A check defined in a shared component is a check that assumes all its users are the same shape.
9 Two machines ran different versions of the same quality tool and disagreed about identical files. Each environment was internally consistent. Only comparing them revealed it. Pin tool versions. When a check disagrees between environments, treat it as a finding, not an inconvenience. Here it was pointing at a real robustness problem in variable naming.
10 The setup tool refused to read its own configuration file because the directory was world-writable (a Windows-mounted filesystem). It simply fell back to defaults silently. No error, no warning. Tools that degrade silently are dangerous. When behaviour differs from expectation, check whether your configuration was read at all.

Category 3 — The ones where the tool lied

#What went wrongWhy it was invisibleThe lesson
11 The model compression tool produced a file that could not be loaded. It reported success. Compression had succeeded. The output was produced correctly. It just could not run — which is a different question. "The tool succeeded" is not evidence the artifact works. Load it and run it before accepting it. The fix was to try candidates and execute each one, keeping the first that actually works.
12 A version number was written without its leading "v", so the security scanner never ran. It failed during setup, before any step executed — so the failure looked like infrastructure flakiness, not a typo. Check that your checks are running. A security check that never executes reports exactly the same thing as one that found nothing.
13 A test alarm endpoint returned "not found" because it did not read the incoming request body first. The response looked like a routing problem, not a request-handling problem. With streaming request bodies, you sometimes must consume the body before responding — even if you do not want it. Read the documentation of your own framework as carefully as you read the ones you are learning.

Category 4 — The performance traps

#What went wrongWhy it was invisibleThe lesson
14 Counting rows after every database write made writes get quadratically slower. The benchmark stalled after a few thousand requests. Each individual check was fast. The problem only appeared at scale, and looked like a benchmark problem rather than a database problem. Never put a growing cost on a hot path. Move maintenance work to a background job — which is also why row cleanup lives in the drift job now.
15 Generating the report took 113 seconds. The statistics were computed in a slow loop. It worked correctly. It was just slow enough that people would stop running it. A tool that is correct but unpleasant gets abandoned. Speed is a feature when it determines whether something is actually used.
16 A database connection context manager does not close the connection — it only manages the transaction. The code read naturally and looked like correct idiomatic Python. A context manager's behaviour is not implied by its appearance. This one leaked a file handle per backup run — invisible on a laptop, quietly fatal on a server running for months.

Category 5 — The statistical traps

#What went wrongWhy it was invisibleThe lesson
17 The drift detector produced about three false alarms every run. Testing 64 features at 5% significance does that by construction. Each individual result was statistically valid. The problem was doing 64 of them at once. Multiple comparisons need correcting. And an alarm that cries wolf gets muted — which is worse than no alarm, because it destroys trust in the whole system.
18 Three features that never vary were included in the drift score, diluting the average and inflating the denominator. They scored 0, which looks harmless. The damage was in the averages, not in the individual values. Exclude things that cannot carry information. A feature that never changes cannot detect change — but it can still distort a summary statistic.
19 Two identical runs gave opposite answers about whether int8 was faster. One said 1.47× slower; the next said 1.75× faster. Each run was internally consistent and produced a confident-looking number. The turning point of the project. It led to measuring the harness's own noise — and to the honest conclusion that the harness cannot resolve its own differences. When your instrument is noisier than your signal, the correct output is "I cannot tell", not the biggest number you saw.
20 A percentile calculation was off by one on exact inputs, because 0.1 cannot be represented exactly in binary. Reported "101 needed" instead of "100". The result was only wrong on round numbers — the exact cases the documentation quoted. Use integer arithmetic when the answer must be exact. Floating-point is fine for estimates and wrong for thresholds. This was caught by a test that checked the documented examples.
21 Deduplicating bin edges would have broken the reference data — producing a different number of bins per feature. Deduplication looks obviously correct. It reduces redundancy. A "cleanup" that makes the data tidier can break the shape your code depends on. Read the comment explaining why the redundant-looking code is there — that comment was written by someone who already made this mistake.

The five patterns behind all twenty-one

1. Silent degradation

Things fall back to defaults, succeed at the wrong thing, or fail where you cannot see. Defence: check that your checks are running.

2. Environment divergence

It works here and not there. Defence: pin versions, and test where you deploy.

3. Scale-dependent bugs

Fine with ten rows, fatal with a million. Defence: think about growth, and test at realistic size.

4. Statistics misapplied

Valid maths, wrong question. Defence: ask what the number would mean if nothing had changed.

5. Trusting the tool's own report

"Success" means it finished, not that it worked. Defence: verify the outcome, not the exit code.

Where will you use this again?

Every one of these patterns will find you again, in a different technology, wearing different clothes. The specific bug — a hash, a version tag, a folder permission — will not repeat. The shape will, constantly.

The skill that matters is not memorising these twenty-one. It is developing the reflex to ask, whenever something looks fine: "what would this look like if it were broken?" That single question is behind most of the fixes above.
