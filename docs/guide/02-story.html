What is in here, and how to read it

Ten minutes of reading here will save you hours later. This page explains the shape of the whole document, and the one habit that makes it easy.

The one habit

Every single part of this document answers four questions in the same order. Once you notice the pattern, you can skim any part and still get what matters:

QuestionWhat it means
What is it? The plain-English name and a picture of the thing. No jargon on the first line, ever.
Why did we need it? The problem that existed before it. This is the important one — tools only make sense as answers to problems.
How does it work here? The specific details in this project, including the real file names and real numbers.
Where will you use this again? Other jobs, other projects, other problems the same idea solves. This is the part that transfers.
Imagine it like this

Someone hands you a bicycle and says "this is a bicycle." That teaches you almost nothing. But if they say "before bicycles, people walked everywhere and it took all day to visit a friend; a bicycle fixes that" — now you understand bicycles, and you will also understand motorbikes, cars and trains. Tools are answers. Learn the question and you have learned the tool.

Where will you use this again?

The four-question habit is not about this project. It is how you read any unfamiliar codebase, any tool you are handed at a new job, and any technology that did not exist last year. "What problem did this exist to solve?" is the single most useful question in software.

PART 1

The whole story in one page

If you only read one page of this document, read this one.

The problem

Imagine you have taught a computer to recognise handwritten numbers. It looks at a small picture of a digit and says "that is a 7." Great. But a brain sitting in a file on your laptop helps nobody.

To be useful, that brain has to become a service — something other programs can ask questions of, over the internet, all day and all night. And the moment you do that, a flood of new problems arrives, none of which are about machine learning at all:

Which version is faster?

There are several ways to run the same brain. Which one should we pay for in production? Guessing is not good enough.

Is it still correct?

If we swap to a smaller, faster version, does it still get the right answers? Someone has to prove it, automatically.

What if the world changes?

The brain learned from old pictures. What if new pictures look different? Nobody notices until the results are quietly wrong.

What if it breaks at 3am?

Someone needs to be told. And someone needs to know the data can be brought back.

The answer

This project is a small, complete, honest machine-learning service — plus every piece of engineering that a real one needs around it, and a benchmark harness that is allowed to tell you the truth, including when the truth is "this measurement is not good enough to conclude anything."

That last part is what makes it unusual. Most benchmarks are built to produce an impressive number. This one is built to produce a defensible one — and when the data does not support a conclusion, it says so out loud instead of picking the flattering reading.

How the pieces fit together

The surprising ending

You might expect the story to finish with "and int8 was 3× faster, so we shipped it." It does not. It finishes like this:

The honest result

The int8 copy of the brain really is 3.5× smaller (151 KB instead of 535 KB) and just as accurate — those are solid facts. But whether it is faster at answering, this harness cannot say. The run-to-run variation on this machine, measured against itself, is a band from 0.58× to 1.71×. Every speedup measured sits inside that band.

So the conclusion is: we proved the size and accuracy wins, and we proved we do not have the evidence to claim a speed win. A weaker project would have reported the biggest number it saw and moved on.

Where will you use this again?

Everywhere performance is discussed. "It is 40% faster" is one of the most common claims in software and one of the least often justified. Learning to ask "compared to what, measured how many times, and how much does the machine vary against itself?" will change how you read every benchmark you ever see — including the ones from companies selling you something.
