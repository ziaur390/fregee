PART 8

The smoke alarm: drift detection

A machine-learning service can fail while every technical check says it is healthy. This is the part that catches that, and it is the most machine-learning-flavoured piece of engineering here.

What is it?

A background job that regularly looks at the pictures people have actually been sending, compares them to the pictures the model learned from, and raises a flag if the two have drifted apart.

Why did we need it?

The problem before it — the silent failure

Imagine your digit model works perfectly. Now imagine that, over months, your users start sending photos taken with a different camera: sharper edges, different lighting, a slightly different way of writing. The model has never seen this style.

What happens? Almost nothing visible. The service stays up. Response times are fine. No errors are logged. Every dashboard is green. The model confidently returns answers — it always returns an answer, because that is all it can do.

It just gets more of them wrong. Silently. And the only way you find out is when a human eventually notices that the results have been bad for weeks.

Imagine it like this

You learned to recognise your friends by their faces. Now everyone starts wearing sunglasses and hats. You still smile and say "hello, Sarah!" — you are not confused, you are not making an error message. You are just wrong more often, and nobody notices, because you sound perfectly confident.

Drift detection is noticing that everyone is wearing hats now.

How does it work here?

The idea: compare shapes of distributions

You cannot compare individual pictures — tomorrow's pictures are naturally different from yesterday's, and that is fine. What you compare is the overall shape of the data.

Imagine it like this

You cannot tell if a class of children has changed by looking at one child. But if you line them all up by height, you get a shape — most in the middle, few at the edges.

Do that every year. If the shape stays the same, the class is the same kind of class. If suddenly everyone is much taller, something changed — even though every individual child is still just "a child."

For each of the 64 pixels, the job asks: do production values fall into the same buckets, in the same proportions, as during training?

The measuring stick: PSI

The score is called Population Stability Index. It compares the share of values in each bucket now versus during training:

PSI scoreVerdictMeaning
under 0.1stableLooks like training data. Nothing to do.
0.1 to 0.25watchSomething is shifting. Keep an eye on it.
over 0.25alertMeaningfully different. Investigate.

These thresholds are the industry convention, which matters more than it might seem: a PSI of 0.3 means the same thing on a big dataset as on a small one, so the number is portable between teams and companies.

Two detectors, and why only one of them decides

The job computes two different statistics. Only one is allowed to raise the alarm. This is a deliberate design decision worth understanding.

MeasureRoleWhy
PSI Decides It is a magnitude — a size, not a yes/no answer. So it does not care how much data you have. Bigger window, smaller window, same meaning.
KS test Corroborates It is a statistical test, which answers "is there any difference?" More data makes it more sensitive — so it eventually finds differences far too small to matter.
The false alarm problem — why KS cannot be in charge

There are 64 features. A statistical test at the usual 5% confidence level falsely fires about once in twenty times by pure chance. Across 64 features, that is roughly 3 false alarms every single run — every run, forever, on data that has not changed at all.

Add the sample-size sensitivity and you get a detector that cries wolf constantly. And the predictable human response to an alarm that fires three times a run is to mute it. At which point you have paid for a smoke alarm and disconnected the battery.

So PSI decides. KS is recorded in the output as supporting evidence — genuinely useful when you are investigating a real alert — but it cannot page anyone.

Three features excluded, on purpose

Every 8×8 digit picture has pixels in the corners that are background in every single training image. Those pixels never change. Across 64 features, 3 of them are completely constant.

Those 3 are excluded from scoring, and the reasoning is worth following because it is a nice piece of clear thinking:

  • A feature that never varies has no distribution. There is no "normal" for it to deviate from.
  • Its PSI is therefore 0 no matter what arrives — you could send it anything and it would score zero.
  • Including it would drag the average PSI down, making real drift in the other 61 features look smaller.
  • It would also inflate the denominator in "what fraction of features drifted?" — making a genuine widespread problem look less widespread.

So they are excluded from scoring — but they are recorded in the output, so nobody later wonders why the numbers do not add up to 64. Hiding it would be worse than the tiny inconsistency it avoids.

Distinguishing "nothing moved" from "nothing was measured"

A quiet design decision with real consequences. The job publishes a metric called mlserve_drift_measured:

ValueMeaning
1The window was compared against the reference and nothing moved. Genuinely healthy.
0The window was too small to compare. Nothing was checked at all.

Without this distinction those two situations look identical — both show "no drift". So a drift job that had been broken and silent for three weeks would look exactly like a perfectly healthy one on every dashboard.

With the distinction, there is a separate alarm: "the drift detector has not run successfully in two hours." That catches the failure that a dashboard fundamentally cannot.

Why we needed this, generally

"Everything looks fine" and "I have no information" are completely different states, and monitoring systems confuse them constantly. A graph with no line on it is not a flat line at zero. Any time you build a system that reports on itself, ask: what does this look like when it is broken? If the answer is "the same as when it is healthy," you have a blind spot.

The alert policy

ConditionVerdict
Any single feature over PSI 0.25alert
More than 20% of features over PSI 0.10alert — many features moving together is a real change
Some features over 0.10, none over 0.25watch — noted, not paged
Nothing over 0.10stable

The reasoning behind the second rule: one feature drifting is usually noise, a measurement quirk, or a feature that is simply unstable. But when a fifth of your inputs move together, that is almost never chance. It means the input has genuinely changed — a new data source, a new camera, a new user population.

Where will you use this again?
  • Any live model in any industry needs this: fraud detection, credit scoring, recommendations, demand forecasting, medical risk. The features differ; the technique is identical.
  • PSI and KS are standard tools in data science and analytics roles. Recognising which one answers which question is a genuine interview differentiator.
  • The multiple-comparisons problem (64 tests means 3 false alarms) appears everywhere data is tested in bulk: A/B testing many metrics, genomics, anomaly detection across many sensors.
  • Distinguishing "no problem" from "no data" is a principle for every dashboard, alert and health check you will ever write.
  • The "false alarms get muted" argument is how you justify spending engineering time on alert quality. An alert nobody trusts is worse than no alert, because it trains people to ignore the system.
PART 9

The photocopy you actually test: backup

Everyone makes backups. Almost nobody knows whether theirs work. This part is about the difference — and it is one of the most practically valuable pieces in the whole project.

What is it?

Two programs. One makes a dated archive of everything important. The other takes that archive, actually restores it, and checks that what came back matches what went in.

Why did we need it?

The problem before it

Writing a backup is easy. A single command, or ten lines of code. It produces a file. Everyone feels safe.

But a backup file is a hypothesis, not a guarantee. It has never been proven to contain what you think. The proof only arrives on the worst day of your professional life: when production data is gone and you reach for the archive.

And that is exactly the moment when you find out the file was truncated, or the database inside it was captured mid-write and is corrupt, or the restore procedure needs a tool you do not have, or the archive was being written to a directory that stopped existing six months ago.

A backup you have never restored is not a backup. It is a wish.

How does it work here?

What actually gets proven

The verifier does not check that the file exists. That would be nearly worthless. It does all of this:

#CheckWhat it would catch
1Open the archive as a real archiveA file that was truncated, or is not actually an archive at all.
2Find the manifest insideAn archive from a different version, or an empty one.
3Verify the checksum of every model fileSilent corruption — a single flipped bit in the model file, which would make it load and quietly predict rubbish.
4Verify the database file checksumThe same, for the data.
5Actually restore the database into a scratch locationA file that is structurally valid but unusable in practice.
6Count the rows in the restored copy and compare to the manifestA restore that "succeeded" but lost data.

Only after all six does it report success — and it raises an error on any mismatch rather than returning a true/false that a caller could ignore.

The bug this design would have caught

The database is copied using SQLite's own backup facility, not by copying the file. That sounds pedantic. It is not.

Why copying a database file is not a backup

A live database is not just the file on disk. Part of its current state lives in memory — pages waiting to be written, a transaction in progress. If you copy the file while it is being written to, you can capture a torn state: half of the old data and half of the new.

The result looks like a perfectly normal database file. It opens. It answers queries. It is just quietly missing or duplicating rows at the moment of the copy.

SQLite's backup API takes a proper, consistent snapshot — it knows how to do this correctly. Using it is one line instead of one line, so there was never a reason to do it the wrong way.

Testing the alarm, not just the safe

There is a subtle testing principle here. A verifier that has only ever been seen to pass has not been tested. It might pass everything — including a corrupt archive.

So the test suite deliberately corrupts an archive and asserts that the verifier rejects it. That is the only way to know the verifier actually checks anything.

Imagine it like this

You install a smoke alarm. You press the test button. It beeps. Good — the alarm works.

But how do you know it would beep for actual smoke, and not only when you press the button? You have to test it with something that is genuinely a problem. That is what corrupting an archive does for this verifier.

Why it is written in Python, not shell

The original plan was a shell script, which is the traditional way to do this. It was changed to Python for one reason: the developer's machine is Windows, where shell scripts cannot be tested.

A backup routine that has never been run is a liability — and the backup path is the last place you want untested code. Writing it in Python means it can be run and tested on every machine, in the test suite, and in the automated checks. The Ansible setup runs this same code on a timer, so nothing is lost.

Where will you use this again?
  • "Verify your restores" is one of the most respected things you can say in a systems interview. It is the standard answer to "how do you know your backups work?" and most candidates do not have it.
  • Checksums for integrity are used everywhere: package managers, download verification, container images, data pipelines, git itself.
  • Testing the failure path — deliberately breaking something to prove the detector notices — is a core discipline. The same idea appears in chaos engineering at large companies.
  • Choosing a testable language over a traditional one happens whenever a script matters enough that being untested is unacceptable. Automation, migration scripts, deployment steps.
  • Row-count and checksum comparison is how you verify any data migration: database upgrades, cloud moves, format changes.
