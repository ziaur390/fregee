PART 4

Three copies of the brain: the runtimes

The same trained model, packaged three different ways. This is the experiment the whole project is built around — so it matters that the three copies really are the same brain.

What is it?

A model's weights are just numbers. But numbers need a program to interpret them, and there is more than one program that can do that. It is like music: the same song can be on a vinyl record, a CD or a streaming file. Same music, different containers, different trade-offs in quality and convenience.

Copy What it is Plain description
TorchScript
model.ts		 The original framework, frozen PyTorch is the library the model was written in. TorchScript takes the model and freezes it into a standalone file that no longer needs your Python code. The originals, essentially unchanged.
ONNX fp32
model.onnx		 A universal interchange format ONNX is a common language that many tools speak. Exporting to it means the model can run on engines that have never heard of PyTorch. Same full-precision numbers.
ONNX int8
model.int8.onnx		 The compressed version Every number in the model is stored in a smaller box. Almost a third of the size. Slightly less precise by construction — the question is whether the lost precision matters.

Why did we need it?

The problem before it

You trained a model in PyTorch. Now you have to run it in production, a million times a day. Do you ship PyTorch? It is enormous, it is slow to start, and it drags in a whole ecosystem of dependencies you do not need.

There are alternatives. Which one is fastest? Which one is smallest? Does the smallest one still get the right answers?

These are ordinary engineering questions with measurable answers — but only if you can compare fairly. That is what this part of the project is.

The most important rule: one brain, three boxes

Here is the trap. Suppose you train three separate models, export each one differently, and compare their speeds. You would learn nothing, because the three models might genuinely be different — different weights, different accuracy. The speed difference could be caused by the model, not the runtime.

So all three copies are exported from exactly the same trained weights file. The only thing that differs between them is the container. Any difference that shows up is caused by the runtime, and nothing else.

How does it work here?

What int8 actually means

This is worth understanding properly, because "quantisation" is one of those words that gets used a lot and explained rarely.

Imagine it like this

You measured your height really carefully: 1.4273 metres. Someone writes it down as "about 1.4 metres."

You lost some detail. But you also used far fewer characters, and for most purposes "about 1.4 metres" is completely fine. Quantisation is exactly this: writing the numbers down with less detail, in exchange for taking up much less space.

And crucially — if the question is "am I taller than the door frame?", both answers are identical. The lost detail did not change the answer.

Technically: normal model numbers are 32-bit floats, which store a number with a decimal point and a lot of precision. int8 stores each number as an integer from −128 to 127 — one byte instead of four. A quarter of the space, and smaller numbers are quicker for a processor to move around.

TypeHow storedSpace eachAnalogy
fp32Decimal, high precision4 bytes1.4273 metres
int8Whole number, −128…1271 byteabout 1.4 metres

3.5×smaller file

So the compression worked perfectly: a third of the size, zero loss in accuracy, zero disagreement with the full-precision version on the test set. Those are excellent, solid results.

The honest limitation

Our int8 model is not fully compressed. Only the "dense" parts of the network were converted. The convolution layers — the image-scanning part — had to stay in full precision, because of a bug described in Part 21.

A proper static-quantisation pipeline would compress those too, and get a smaller file than 151 KB. We recorded this in the artifact's metadata and stated it in the report, rather than presenting 3.5× as the best achievable.

Why admit it? Because someone reading "3.5× smaller" might reasonably assume that is the limit of the technique, and go on to make a bad decision later. Naming your own ceiling is part of reporting a result honestly.

The parity check: turning agreement into a gate

After exporting, the code runs all three copies over the same 270 exam pictures and compares their answers:

RuntimeTolerance for disagreementWhy
TorchScript0%It is the reference. Nothing to compare against.
ONNX fp320%Same numbers in a different format — it should be exactly identical.
ONNX int8up to 2%Compression loses detail by design. A little disagreement is expected and acceptable.

If any copy exceeds its tolerance, the export fails the build. Not a warning printed and ignored — an actual failure that stops everything.

Why failing the build matters so much here

A broken export is the worst possible bug for this project, because it produces plausible-looking numbers. If the int8 model were quietly wrong, the benchmark would happily report "int8 is fast!" while it was actually just guessing. Every subsequent conclusion would be built on sand.

Warnings get ignored. A build failure cannot be. So the check is a gate, not a note.

Where will you use this again?
  • Model compression is standard practice for putting models on phones, in browsers, on cheap hardware, or anywhere memory is expensive. The same trade-off — size and speed against precision — appears every time.
  • ONNX specifically is how models move between tools. "I trained it in PyTorch but need it in a C++ program" is a solved problem, and ONNX is usually the answer.
  • Parity testing — proving that a rewritten, optimised or compressed version of something behaves identically — is a general technique. It applies to database migrations, language rewrites, and compiler changes, not just models.
  • Making a check fail the build rather than printing a warning is a habit worth adopting everywhere. It is the difference between a check that exists and a check that works.
PART 5

The shop counter: the API

The model is a brain in a jar. The API is how the outside world talks to it. This part explains what a web service actually is, and the small decisions that separate a service you can trust from one you cannot.

What is it?

A program that sits and waits for other programs to ask it questions over the network. It listens at an address, understands a few specific requests, and sends back answers.

Imagine it like this

A restaurant. You do not walk into the kitchen and start cooking. You sit at a table, order from a menu, and a waiter takes your order to the kitchen and brings back your food.

The menu is the API. It lists exactly what you are allowed to ask for and how to ask for it. The waiter is the code that receives your request and passes it along. And a good waiter does something else important: if you order something not on the menu, they tell you clearly, rather than bringing you a random plate of food and hoping.

Why did we need it?

The problem before it

Without an API, using your model means: install Python, install the right libraries, write code that loads your model file, and call it. That only works for people who are programmers, on machines where all of that is installed.

With an API, anything that can make a network request can use your model. A phone app, a spreadsheet, a tiny script in any language, a website. The model becomes a service rather than a file.

How does it work here?

The endpoints — the menu

AddressTypeWhat it does

That last one is worth pausing on. /docs is generated automatically from the code itself, so it cannot fall out of date. If you open http://localhost:8000/docs you get a page where you can look at every endpoint, see exactly what it expects, and click a button to try it. Nobody wrote that page by hand.

Liveness versus readiness — the distinction that trips everyone up

This is one of the most commonly misunderstood ideas in running services, and getting it wrong causes outages. So here it is carefully.

SignalQuestionWhat should happen if it fails
Liveness
/healthz		 "Is this process still running, or has it frozen?" Restart it. A frozen process will never recover on its own.
Readiness
/readyz		 "Should I send it traffic right now?" Do not restart it. Just stop sending requests until it is ready. It may be starting up, or waiting for something.
The mistake, and why it is so damaging

Most people wire the model check into liveness. The reasoning seems sensible: "if the model is broken, the service is broken, so restart it."

Here is what actually happens. A bad release ships a broken model. Every copy of the service reports "not alive." The orchestrator dutifully restarts all of them. They come up, load the same broken model, and report "not alive" again. Restart. Restart. Restart.

You now have two problems. The original broken model — and a restart storm hammering your system, making logs unreadable and masking the real cause. The original error is buried under thousands of identical restart messages.

Keeping them separate means a broken model produces exactly one clear signal: "ready, but not ready to serve" — and the service just quietly sits out of rotation, logging one honest error. That is far easier to diagnose at 3am.

Things this API does that a naive one would not

Request logging happens after answering

Saving a row to the database is slow. If it happened before answering, the customer would wait for it — and worse, the benchmark would measure database speed and call it inference speed. So it is queued as a background task.

Oversized batches are rejected, not trimmed

Send 1,000 pictures, get an error saying the limit is 64. A friendlier-looking service might silently process the first 64 and return those answers — but then your program believes it has 1,000 results and quietly loses 936. A clear failure beats a silent wrong answer, always.

Errors return errors, not 500s

If you send nonsense, you get a 422 "your request was malformed" with a readable explanation — not a 500 "something exploded", which tells you nothing and suggests the server is at fault.

Confidence, not just an answer

Every prediction comes with a percentage. "It is a 7, and I am 99.4% sure" is far more useful than "7" — because a low-confidence answer is a signal that the input is unusual.

A worked example

# Ask the service about one 8x8 picture, using the int8 runtime
curl -X POST "http://localhost:8000/predict?runtime=onnx-int8" \
  -H "Content-Type: application/json" \
  -d '{"features": [0,0,5,13,9,1,0,0, 0,0,13,15,10,15,5,0, ... ]}'

# Answer:
{
  "predictions": [
    {
      "predicted_class": 7,
      "confidence": 0.994,
      "probabilities": [0.001, 0.000, ... ]
    }
  ],
  "runtime": "onnx-int8",
  "batch_size": 1,
  "latency_ms": 3.41
}

Note the ?runtime= in the address. That is how the benchmark tests all three runtimes through the exact same service — one small switch, so that everything else about the request stays identical.

Where will you use this again?
  • Liveness versus readiness is used by Kubernetes, Docker Swarm, AWS load balancers, Azure, and every orchestrator. Getting this distinction right is a standard expectation in DevOps and platform roles.
  • Background tasks for slow side-effects — logging, sending emails, updating a cache — appear in every web service you will ever work on.
  • Rejecting bad input loudly instead of silently adjusting it is a principle that applies to every interface you design, including command-line tools and internal function calls.
  • Auto-generated API documentation (this project uses FastAPI's built-in ability) is how modern teams keep documentation honest. If you have ever used a service whose docs were wrong, you know why this matters.
