PART 12

The whole kitchen: Docker Compose

Nine separate programs that must start in the correct order, find each other, and share data. This is the file that describes the entire system in one place.

What is it?

A single text file listing every piece of the running system — what each one is, how it is configured, what it needs, and in what order things must happen.

Why did we need it?

The problem before it

Our system is not one program. It is nine: the model builder, the API, the drift job, the backup job, four monitoring programs, and a small test server. Each one needs the right settings, the right folders connected, and the right ports.

Without a single description, starting the system means typing nine long commands in the right order, remembering every setting, and hoping you got them all right. Nobody can reproduce that, and nobody can review it.

How does it work here?

The startup order — and why it cannot be guessed

The race condition this prevents

The API cannot serve predictions without model files. If both containers started at the same time, there would be a window where the API is running but its model files do not exist yet. It would report "not ready" — correctly — and then become ready a few seconds later.

That sounds harmless. It is not, because it happens on every single start. Automated systems that check health see a service that is intermittently unavailable, and may make decisions based on that — restart it, take it out of rotation, page someone.

Waiting for the model builder to finish successfully removes the window entirely. The API never exists in a state where it cannot serve.

Data that must outlive the containers

Containers are disposable. Delete one and everything inside it is gone. But the model files, the request log, the results and the backups must survive. So each gets a named volume — a storage area that exists separately from any container.

VolumeHoldsWho can write
artifactsThe three model files, the drift referenceinit writes; api and drift read only
dataThe request log databaseapi, drift
resultsBenchmark output, drift reportdrift, init
backupsBackup archivesbackup
drift-textfileThe drift numbers, in a format Prometheus can readdrift writes; node-exporter read only

Note the read-only ones. The API does not need to change the model files — only read them. So it is given read-only access. If the API were ever compromised, it could not corrupt the model the whole system depends on. That is one word in a config file buying a real safety property.

Small decisions with outsized effects

Ports are adjustable

Everything the project listens on can be moved with a setting. Most developers already have something on port 8000 or 3000. A project whose first instruction fails with "port already in use" makes a bad first impression.

Timers are loops, not cron

The drift and backup jobs are written as a simple loop with a sleep. One less program to run, and the interval is visible on a single line instead of buried in a scheduling file.

An exit code of 2 is not a failure

The drift job exits with code 2 when it finds drift. That is a finding, not a crash. The loop distinguishes them, so a real drift alert does not look like a broken container.

Postgres is commented out on purpose

A second database is included but disabled, with instructions. The restore-verification code only supports the primary one — and shipping a database whose backup cannot be proven would be worse than not offering it.

Where will you use this again?
  • Compose for local development is nearly universal. Almost every backend project has one. Being able to read and write one is a baseline skill.
  • Startup ordering and health gates carry directly into Kubernetes (readiness probes, init containers) — the concepts are identical, only the vocabulary changes.
  • Named volumes and read-only mounts are how state is managed in all container systems.
  • Not shipping what you cannot verify — the disabled Postgres — is a judgement call interviewers notice. It is more impressive than offering every option.
PART 13

The dashboard and the alarm bell: monitoring

Three programs that answer three different questions: what is happening, what does it look like, and who needs to know.

What is it?

Prometheus — the record keeper

Every 15 seconds it asks the API "what are your numbers?" and stores the answers with timestamps. It keeps 15 days of history.

Alertmanager — the decision maker

When a rule fires, this decides who to tell, whether to repeat, and when to stop. It handles the annoying human problems: not sending 400 copies of the same alert.

Grafana — the picture maker

Turns stored numbers into graphs a human can read at a glance. Pre-configured, so it works the moment you open it.

alert-sink — the tester

A deliberately tiny web server whose only job is to receive alerts and print them. It exists so we can prove the whole alerting chain works, rather than assuming it does.

Why did we need it?

The problem before it

Without monitoring, you learn about problems from users. "The app is slow" is what you get instead of "response times crossed 50 ms at 14:02."

And without alerting, nobody knows at 3am. The service could be fully broken and the first anyone hears is at 9am when someone tries to use it.

How does it work here?

The numbers the API publishes

MetricAnswers
mlserve_requests_totalHow many requests, broken down by endpoint and result.
mlserve_request_duration_secondsHow long they took — this is what produces p50, p95 and p99.
mlserve_batch_sizeHow many pictures arrived per request.
mlserve_model_loadedIs the model actually loaded right now? 1 or 0.
mlserve_model_size_bytesHow big each runtime's file is.
mlserve_validation_errors_totalHow many requests were rejected as malformed.
mlserve_inference_errors_totalHow many times the model itself failed.
mlserve_db_write_errors_totalHow many times a log write failed — a signal the database is in trouble.
mlserve_predictions_totalWhat the model has been predicting, by digit. If it starts saying "3" for everything, this shows it.

Special values called "histograms"

Latency is not a single number — it is a distribution. A histogram stores how many requests fell into each speed range. That is what allows the system to calculate "how slow was the slowest one in a hundred?"

That last one deserves a moment. Most monitoring systems will happily draw a p99 from four data points and present it as fact. This one raises a flag saying "there is not enough data for this number to mean anything" — the same honesty principle from Part 7, carried all the way into the live dashboard.

The awkward problem: the drift job has no web address

Prometheus collects numbers by asking services over the network. But the drift job is not a service — it runs, does its work, and exits. There is nothing to ask.

The traditional answer is a "push gateway": the job pushes its numbers somewhere and Prometheus reads them from there. That means running another container, plus the constant risk that Prometheus reads the numbers at a bad moment.

Our solution is simpler: the drift job writes its numbers to a file, and a small existing component reads that file. Two lines of configuration, no extra container, no timing window.

And the file is written by creating a temporary file and then renaming it — because renaming is instant and atomic. A reader either sees the old complete file or the new complete file, never a half-written one. Without this, Prometheus would occasionally read a partial file, fail to parse it, and produce a random dip in your graphs.

Where will you use this again?
  • Prometheus and Grafana are close to industry standard for infrastructure monitoring. Reading a PromQL query or editing a dashboard is a common job requirement.
  • The three-way split — collect, decide, display — is the right mental model for any monitoring system, including cloud-native ones where the names differ.
  • Alert rules need as much thought as code. Every rule you write is a promise to wake someone up. Rules that fire when nothing is actionable actively make systems less reliable.
  • Monitoring your monitoring — the "detector is stale" rule — is the mark of someone who has been on call. Systems fail in ways their own dashboards cannot show.
  • Atomic file writes via rename is a genuinely useful trick for any situation where one program writes and another reads: log files, caches, lock files, config reloads.
