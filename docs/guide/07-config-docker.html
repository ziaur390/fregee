PART 10

The settings drawer, and the remote control

Two small pieces of housekeeping that make everything else pleasant to use. Neither is exciting; both are the difference between a project people can work with and one they avoid.

What is it? — the settings drawer

Four small text files in configs/ that hold every number the project uses. Want to try 128 pictures per batch instead of 64? Change one line in a text file. No code editing, no searching through thousands of lines for a magic number.

FileHolds
configs/model.yaml How big the network is, the seed (1337), how the data is split.
configs/serving.yaml Which runtime is the default, the maximum batch size, whether to log requests.
configs/bench.yaml The whole benchmark matrix: how many calls, how many repeats, batch sizes, concurrency levels.
configs/drift.yaml Bucket count, minimum window size, and the PSI thresholds.

Why did we need it?

The problem before it

Numbers scattered through the code are one of the most common sources of quiet confusion. Someone changes a batch size in one place and not another. Two parts of the system disagree about how big a batch is allowed to be, and the bug is invisible until something fails in production.

Worse: nobody can see the whole picture. What are the current settings? You would have to read the entire codebase to find out.

With config files, everything important is visible in four short files. And each one carries its reasoning as comments — why the batch limit is 64, why the seed is 1337, why the bucket count is 10. Six months later, those comments are what stops someone from "fixing" a number that was deliberate.

A detail that matters: environment variables

Some settings can be overridden without editing the file at all, using environment variables — small named values that a program reads when it starts.

# Run a quick benchmark in CI without touching the config
MLSERVE_BENCH_CALLS=10 MLSERVE_BENCH_REPEATS=1 python tasks.py bench

# Write results somewhere other than ./results
MLSERVE_RESULTS=/tmp/myrun python tasks.py bench

This is how one configuration serves two purposes: a real, thorough run on a laptop, and a fast smoke test in automation. The file holds the settings a report is pinned to; the environment handles temporary variation.

A real bug this caused, and its lesson

There is a setting that decides where results get written. On a developer's machine it defaults to a folder inside the project, which is writable. Inside the container, that same default pointed at a folder owned by the system administrator account, and the service deliberately runs as an unprivileged user.

Result: the drift job crashed with "permission denied", every time, only in the container. It worked perfectly on every developer machine — which is why it survived so long.

The lesson: "it works on my machine" is usually not carelessness. It is a genuinely different environment. Defaults that resolve relative to the code's location behave differently when the code is moved somewhere with different permissions. This is why the fix was to set the path explicitly in the container, with a comment explaining why the line must not be deleted.

What is it? — the remote control

A single file, tasks.py, that gives every project action a short name.

python tasks.py test      # run the checks
python tasks.py bench     # run the benchmark
python tasks.py report    # build the report
python tasks.py verify    # do everything, end to end

Why did we need it?

The problem before it

Real projects need long, fiddly commands with the right environment, the right paths and the right order. Nobody remembers them. People copy them out of old chat messages and get them slightly wrong.

And there is a worse problem: the commands live in one person's memory. A new contributor has to be told everything.

With a task runner, there is one place to look. Running python tasks.py with no arguments lists every available action with a description, so the project explains itself.

Why Python instead of the usual tool

Everyone in this field has heard of make, which is the traditional way to do this. But make is not installed on Windows by default, and this project must work on the developer's actual machine.

Installing extra software to run your own project is friction, and friction is what makes people stop working on things. So the tasks are written in plain Python using only the standard library — which means if you have Python, you can run the project. No installation step at all.

A Makefile is provided too, so people on Linux who instinctively type make test are not surprised. It simply forwards to the same Python file. Two doors, one room.

Where will you use this again?
  • Task runners of some kind exist in every mature project — make, just, npm scripts, rake, invoke, Taskfile. The concept is universal even when the tool differs.
  • Config files with comments explaining the reasoning are how you leave notes for the future. Code tells you what; a comment next to a threshold tells you why it is that number and not another.
  • Environment variable overrides are the standard way to configure the same software for development, testing and production without maintaining separate copies.
  • Choosing your own tools to fit the environment rather than following tradition — and explaining the choice — is a judgement you will be asked to make repeatedly.
PART 11

The lunchbox: Docker

The tool that ended the phrase "but it works on my machine." This part explains what containers actually are, and the specific decisions that make this particular image good.

What is it?

A way of packaging a program together with everything it needs to run — the right version of Python, the right libraries, the right system settings — into a single sealed unit.

Imagine it like this

Your friend says "I made you lunch, come get it." You arrive and they say "oh, but you need to bring your own plate, and a fork, and my kitchen only works on Tuesdays."

A lunchbox solves this. The food, the plate, the fork and the napkin are all inside. Hand it to anyone, anywhere, and they can eat. That is what Docker does for software.

Why did we need it?

The problem before it

Our program needs Python, plus about eight libraries, each with its own specific version. Different versions of those libraries behave differently. Your laptop has one combination; the server has another; the automation machine has a third.

So the program works on your machine and mysteriously fails elsewhere. Hours disappear into "which version of numpy do you have?"

Containers make the environment part of the software. There is no "which version do you have" — the version is fixed inside the box.

How does it work here?

The two-stage build

This is the most interesting decision in the Dockerfile, and it solves a problem that surprises people.

Why this matters for security, not just size

Compilers are tools for turning source code into programs. If an attacker gets into your container, a compiler is one of the most useful things they could find — it lets them build their own tools inside your system.

Removing compilers from the shipped image is therefore both smaller and safer. This is a standard practice with a name — minimising the attack surface — and it is exactly what the two-stage build achieves almost for free.

Four more decisions, each solving a real problem

DecisionProblem it solves
Install torch from the CPU-only source The default version of the machine-learning library ships with GPU support and pulls in roughly 2.5 GB of graphics-driver libraries. This service runs on a processor and never touches a GPU. Pointing the installer at the CPU-only source is one line, and removes gigabytes of dead weight. Verified: zero GPU packages in the final image.
Run as a non-root user By default, container programs run with full administrator rights. If someone finds a way in, they own everything. Running as an ordinary restricted user means a break-in is contained. Costs one line; is a genuine security boundary.
Create the data folders as the service user Containers can only write to folders they are given, and a folder that does not already exist gets created by the administrator account. The service then cannot write to its own data directory. Creating the folders up front, owned by the right user, prevents a whole category of confusing permission failures.
Check writability at build time One extra line that tries to write a file into each data folder during the build. If any folder is not writable, the build fails immediately — rather than the service failing at 2am. Failing fast, early, and loudly is almost always the right trade.

The health check that was deliberately removed

The Dockerfile contains a comment explaining something that is not there:

# No HEALTHCHECK here, deliberately. This image is used by five different roles
# (init, api, drift, drift-publisher, backup) and only one of them serves HTTP,
# so an image-level healthcheck is wrong by construction.
What went wrong

The image originally had a health check that tried to reach a web address. Five different jobs use this image, but only one of them is a web service. The other four — the model builder, the drift job, the backup job — have no web address to check.

So four out of nine containers permanently reported "unhealthy" — while working perfectly. Worse, the command that starts everything up and waits for health checks never returned. Starting the project appeared to hang forever.

The fix: move health checks out of the image and into the file that describes the stack, where each service can be checked for what it actually does. A liveness check belongs to the thing being checked, not to the tool it was built with.

Where will you use this again?
  • Docker is close to universal in backend, DevOps, platform and data roles. Understanding images versus containers, layers, and multi-stage builds is expected knowledge.
  • Multi-stage builds are the standard way to keep production images small in any compiled language — Go, Rust, Java, C++.
  • Running as non-root is required by many security policies and is a frequent security-review finding when missed.
  • Failing the build rather than the runtime is a general principle: catch problems as early as possible, when they are cheap and obvious.
  • Putting the check where the knowledge is — the health check next to the service definition, not in the shared image — is a design instinct that applies far beyond Docker.
