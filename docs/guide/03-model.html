PART 2

Sixteen words you need first

Every word below appears later in this document. Read them once now, and nothing further will confuse you. You do not need to memorise them — they are all repeated in the glossary at the end.

Words about the brain

WordWhat it means, plainly
Model A computer program that has learned from examples instead of being told the rules. Here: one that recognises handwritten digits. Also called "the brain" in this document.
Training Showing the model thousands of examples with the right answers attached, and letting it adjust itself until it gets them right. Like practising with a workbook that has the answers in the back.
Neural network The particular style of model used here. It is a stack of very simple maths steps, each passing its result to the next. Nothing about it is like a real brain, despite the name.
Weights The numbers inside the model that training adjusts. Training's entire output is a big pile of weights. Here: 136,586 of them.
Parameters Another word for those same numbers. "A 136k-parameter model" means "a model with 136,000 adjustable numbers."
Inference Using a trained model to answer a question. Training is the studying; inference is the exam. This document mostly cares about inference, because that is what production does millions of times.
Accuracy The share of questions it got right. 0.9741 means 97.41 times out of 100.

Words about shipping it

WordWhat it means, plainly
Runtime The program that runs the model — the engine, not the fuel. Different engines can run the same weights at different speeds.
API Application Programming Interface. A fixed set of questions that one program agrees to answer for another. Like a restaurant menu: you do not walk into the kitchen, you order from the list.
Endpoint One specific item on that menu — one address that does one thing. /predict is an endpoint.
Latency How long one request takes, in milliseconds. Lower is better. The number everyone argues about.
Throughput How many requests you can handle per second. Related to latency but not the same thing — like how a shop can be slow per customer but serve many customers at once.
p50 / p95 / p99 Percentiles. p50 is the middle request ("half are faster than this"). p99 is the slow one in a hundred. p99 matters most, because a slow request is often a broken one. Also the hardest to measure — see Part 7.
Batch A group of questions sent together in one request. Usually faster per question than sending them one at a time, because some costs are paid once per batch rather than once per question.

Words about trusting the numbers

WordWhat it means, plainly
Reproducible Run it again, get the same answer. This is the single most important property of a benchmark and the easiest to lose by accident.
Confidence interval A range that probably contains the true value. "1.23× [1.15, 1.31]" means the measured speedup is 1.23 and we are fairly sure the real one is between 1.15 and 1.31.
Noise Random variation that has nothing to do with what you are measuring — a background program waking up, the processor getting warm. The enemy of Part 7.
Drift When the real world slowly stops resembling the examples the model learned from, so its answers quietly get worse. Drift as a verb: the input distribution has drifted.
Why we needed this page

Technical writing usually fails at exactly one place: it uses a word the reader has never seen, on the assumption that the reader has seen it. Nobody admits confusion at that point; they just stop reading. Sixteen words is a small price for the rest of the document being readable.

Where will you use this again?

These sixteen words are the shared vocabulary of the entire industry. They appear in job advertisements, code reviews and interviews regardless of language, company or framework. Knowing them precisely — particularly the difference between latency and throughput, and between p50 and p99 — is the difference between sounding like you have used these tools and actually having used them.

PART 3

The brain: a machine that reads digits

Everything else in this project exists to serve this one small thing. So it is worth understanding it properly — and worth understanding why we deliberately made it small.

What is it?

A neural network that looks at a tiny 8×8 picture of a handwritten digit and says which digit it is, from 0 to 9. The picture is only 64 pixels — about the size of the icons on an old phone screen.

8×8pixels per picture
1,797pictures in the dataset
136,586adjustable numbers
97.41%correct on unseen pictures
~4 sto train on a laptop

Why did we need it?

The problem before it

This project is not really about digit recognition. It is about the machinery around a model — how you serve it, measure it, watch it and protect it. But you cannot demonstrate machinery without something to put inside it.

So we needed a real model — one that genuinely trains and genuinely predicts — that was also small enough to make every other part of the project practical. Those two requirements pull against each other, and the whole design of the model is the compromise between them.

Why not use a big impressive model?

This is the most important design decision in the project, so here is the reasoning spelled out.

If we used a large modelWhat would break
Training takes hours on a GPU Nobody can run it to check your work. Every claim becomes "trust me, it worked on my machine."
It costs money to run The project's rule is zero cost. A free-tier machine cannot train a large model.
It needs to download gigabytes The benchmark would be measuring your internet connection on the first run and nothing on later runs.
The model file is hundreds of megabytes Comparing "535 KB vs 151 KB" would be a rounding error lost in the noise. The size experiment would prove nothing.
Timing differences get large Sounds good — but then the benchmark's careful statistics have nothing interesting to say. The interesting lesson is precisely that small differences are hard to measure.

The model is small on purpose. The model is not the subject of this project; the rigour around it is.

How does it work here?

The data

The pictures come from sklearn.datasets.load_digits, which is bundled inside an already-installed library. Two consequences, both deliberate:

  • No download. The benchmark works with the network switched off, on a plane, or inside a locked-down build machine that is not allowed to fetch anything.
  • Identical for everyone. If the data were downloaded, two people could silently get different versions and their results would not be comparable. Here, "run it again and get the same answer" is true by construction.

Splitting the data — and one mistake that ruins everything

The 1,797 pictures are divided into three groups:

GroupShareWhat it is for
Train70%The workbook with answers. The model learns from these.
Validation15%A mock exam, used while tuning. The model never learns from these directly.
Test15%The real exam, opened once at the end. This is where "97.41% accurate" comes from.
The mistake this avoids — data leakage

Suppose you wanted to make the numbers look good. You could let the model see the test pictures during training. It would then score ~100% on the test — and be useless in the real world, because in the real world it will never see those pictures again.

This is called leakage, and it is the single most common way machine-learning results become fiction. It is rarely done on purpose. It happens by accident, and it is invisible in the output — the numbers just look slightly too good.

There is a subtle version of it in this project. The pictures are normalised (rescaled) by dividing by 16. If that rescaling had been computed over all the pictures including the test ones, the test data would have influenced the model's inputs — a tiny leak, and a leak all the same. In src/mlserve/model.py the statistics come from the training split only, and the code comments say why.

The network itself

The architecture is two "convolution" layers followed by a small decision layer. Convolution is the trick that made image recognition work: instead of looking at all 64 pixels at once, the network slides a small 3×3 window across the picture looking for tiny local patterns — an edge, a corner, a stroke. Then it looks for patterns among those patterns.

Why the model is shaped this way

ChoiceReason
Two convolution layers, not twenty It has to be simple enough that the exported ONNX file is readable when opened in a graph viewer. A 50-layer network produces a diagram nobody can check.
Padding of 1 on the 3×3 windows Keeps the picture 8×8 throughout, so the arithmetic is easy to follow. It also means the flatten step has a predictable size.
Plain code, no clever tricks torch.jit.script (Part 4) compiles this to a standalone file. It refuses to compile unusual or highly dynamic code. Writing boring code here makes the export work.
Dropout of 0.1 Randomly ignores 10% of connections during training, which stops the model memorising the training pictures. This is the standard guard against overfitting — being good at the workbook and bad at the exam.
Seed 1337 everywhere Computers generate "random" numbers from a starting value. Fix that value and the randomness repeats exactly. It is the difference between a rerun and a different run.

About the seed — a small idea with big consequences

Why we needed a seed

Training involves randomness: the order pictures are shown, the initial weights, the dropout mask. Without a fixed starting point, running training twice gives two slightly different models — and then two slightly different accuracies, and no way to tell whether a change you made mattered or whether you just got a luckier shuffle.

Fixing the seed makes every run identical. It is the foundation of the entire reproducibility claim: the same command produces the same numbers, on your machine and mine.

A trap we hit: the seed that was not being set

A subtler version of this bit us in the benchmark. Python deliberately randomises certain internal hash values every time it starts — a security feature, so that an attacker cannot predict them. Our benchmark was using those values to decide which pictures to time.

The result: each run timed a different sequence of pictures, so two runs of the identical command were not comparable, and the difference was indistinguishable from ordinary timing noise. It looked like normal measurement wobble. It was a bug.

The fix: replace the built-in hashing with SHA-256, which is identical in every process and every version of Python. See Part 21 for the full story.

Where will you use this again?
  • Train/test splitting and leakage apply to every model you ever build, in any framework. The accidental version — computing a scaling factor or a filter over all your data — is the one that catches people.
  • Random seeds matter in any reproducible work: simulations, tests that involve randomness, data splitting, anywhere a result depends on a shuffle.
  • Deliberately choosing a small model to make everything else testable is a professional judgement, not a shortcut. Being able to explain why the small model is the right choice is what distinguishes engineering from showing off.
  • Convolution — looking for small local patterns and combining them — is the idea behind virtually all image and audio models in use today.
