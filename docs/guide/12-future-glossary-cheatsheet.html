Where you will use each of these things

Every tool in this project, and the real-world problems it solves elsewhere. This is the transferable part — what you take with you when you leave this repository behind.

Thing What it is really for Where you will meet it again
PyTorch Building and training models Research, computer vision, natural language processing, recommendation systems, forecasting. The dominant framework in industry and academia.
ONNX Moving a model between tools Running models in browsers, phone apps, C++ and Rust programs, or on specialised hardware. Anywhere your training framework is not available.
int8 compression Making models smaller and cheaper On-device machine learning, embedded systems, edge devices, anywhere memory or bandwidth is limited. Also used to reduce cloud inference costs.
FastAPI Turning code into a web service Backend APIs, microservices, internal tools, data services. One of the most common Python web frameworks in new projects.
Liveness vs readiness Letting systems know your state honestly Kubernetes, Docker Swarm, cloud load balancers, service meshes. Getting this wrong is one of the top causes of production outages.
Benchmarking Deciding between options with evidence Database selection, framework choices, hardware sizing, cloud instance types, compiler flags, query tuning. Any decision where "it feels faster" is not good enough.
Confidence intervals Quantifying uncertainty A/B testing, capacity planning, load testing, forecast accuracy, survey analysis. Anywhere a single number would be misleading.
Bootstrapping Uncertainty without assuming a distribution Latency analysis, financial modelling, biological data, any measurement with a long tail. The modern default because it makes fewer assumptions.
PSI / drift detection Noticing when reality changes Fraud detection, credit risk, ad targeting, medical monitoring, demand forecasting, predictive maintenance. Any model deployed into a world that keeps moving.
Verified restore Knowing your data can actually come back Every system with data worth keeping. Required by most compliance regimes, and the first thing asked about in any serious operational review.
Checksums Detecting silent corruption Package managers, container registries, downloads, backups, data pipelines, version control, filesystem integrity.
Docker Consistent software environments Nearly all backend and data work. Local development, testing, deployment, batch jobs, CI.
Docker Compose Describing a multi-part system Local development environments, integration testing, small production deployments, demos.
Prometheus Storing and querying metrics Infrastructure and application monitoring at almost any scale. Its query language is a widely-required skill.
Grafana Visualising what is happening Every operations team, dashboards for business metrics, incident investigation, capacity planning.
Alertmanager Deciding who to disturb and when On-call systems, incident response, escalation policies. The difference between alerting that helps and alerting people turn off.
Ansible Configuring servers consistently Server provisioning, configuration management, deployment automation, compliance enforcement across fleets.
Terraform Creating infrastructure from a description Cloud provisioning on AWS, Azure, Google Cloud or any of dozens of providers. The standard tool for infrastructure as code.
GitHub Actions Automating checks and releases Every professional software team. Testing, building, publishing, deploying, security scanning.
Ruff Catching style and simple bugs automatically Python projects of all sizes. Replacing several older tools because it is dramatically faster.
pytest Proving your code does what you think Universally used in Python. The skill of what to test matters far more than the framework.
Automated dependency updates Staying current and secure Any maintained codebase. Most breaches exploit known vulnerabilities in outdated dependencies, so this is a genuine security control, not housekeeping.

Skills, not tools

Tools change. These do not, and this project exercises all of them:

Reading before writing

Understanding the whole flow before changing anything. The single biggest difference between a fix and a new bug.

Measuring instead of guessing

Reaching for evidence before opinion — and being willing to report that the evidence is inconclusive.

Designing for failure

Asking "what happens when this breaks?" at design time rather than discovery time.

Being honest about limits

Stating what was not tested, what could not be resolved, and what you got wrong. This is rare enough to be a differentiator.

Making the cheap choice deliberately

Not every problem deserves a sophisticated solution. Knowing when something is good enough — and being able to justify it — is senior-level judgement.

Writing for the next person

Comments that explain why, not what. Documentation that states limitations. The person you are helping is usually future-you.

Glossary

Every term used in this document, in one place. Alphabetical, so you can jump straight to the one you have forgotten.

TermPlain meaning
AccuracyShare of predictions that were correct. 0.9741 means 97.41%.
AlertAn automatic notification that something needs attention.
AlertmanagerThe program that decides who to notify when a monitoring rule fires, and stops repeats.
AnsibleA tool that configures computers from a written description, safely repeatable.
APIA fixed set of questions one program agrees to answer for another.
ArtifactA file produced by a build process — here, the exported model files.
BatchSeveral items sent together in one request.
BootstrapEstimating uncertainty by resampling your existing data many times.
ChecksumA short code computed from a file's contents. If the file changes at all, the code changes. Used to detect corruption.
CI / Continuous IntegrationRunning automatic checks on every change.
ConcurrencySeveral things happening at the same time.
Confidence intervalA range that probably contains the true value.
ContainerA sealed package of a program plus everything it needs to run.
DriftWhen real-world data gradually stops resembling the data a model learned from.
DockerThe most common tool for building and running containers.
EndpointOne specific address that performs one specific job.
Environment variableA named setting passed to a program when it starts.
fp32The standard way to store model numbers: high precision, 4 bytes each.
FastAPIA Python framework for building web services; generates documentation automatically.
GrafanaA program that draws stored numbers as charts and dashboards.
HistogramA record of how many values fell into each of several ranges. How latency distributions are stored.
HTTPThe language web browsers and services use to talk to each other.
IdempotentSafe to run repeatedly: doing it twice has the same effect as doing it once.
InferenceUsing a trained model to answer a question. The exam, not the studying.
int8Storing model numbers as small whole numbers: less precise, but a quarter of the size.
JSONA simple text format for structured data — the standard way services exchange information.
KS testA statistical test for whether two sets of values differ. Sensitive to sample size, so used here only as supporting evidence.
LatencyHow long one request takes.
Liveness"Is this process still running?" Failure means restart it.
MetricA number recorded over time so it can be watched.
ModelA program that learned from examples rather than being told rules.
Neural networkA stack of simple maths steps, each passing its result to the next.
Noise floorThe smallest difference an instrument can reliably detect. Measured here by comparing identical things.
ONNXA common format for models, so different tools can run the same one.
OverfittingBeing excellent at the practice questions and bad at the real exam.
p50 / p95 / p99Percentiles: the middle request, the slowest 1 in 20, the slowest 1 in 100.
Parity checkProving two versions of the same thing behave identically.
PercentileThe value below which a given share of observations fall.
PrometheusA program that collects and stores metrics over time.
PSIPopulation Stability Index. A number describing how much a distribution has shifted. Sample-size independent, so it is what decides here.
QuantisationStoring numbers with less precision to save space. "About 1.4 metres" instead of "1.4273 metres".
Readiness"Can this serve traffic right now?" Failure means stop sending requests, not restart.
ReproducibleRunning it again produces the same result.
RuntimeThe program that runs a model — the engine, not the fuel.
SeedThe starting value for a random number generator. Fix it and the randomness repeats exactly.
SQLiteA database that lives entirely in one file. No server to run.
Systemd timerA Linux feature for running a command on a schedule.
TerraformA tool that creates cloud infrastructure from a written description.
ThroughputHow many requests can be handled per second.
TorchScriptA frozen, standalone version of a PyTorch model that does not need your Python code.
TrainingShowing a model many examples with correct answers so it adjusts itself.
VarianceHow much measurements spread out. High variance means noisy.
Volume (Docker)A storage area that outlives containers.
Weights / parametersThe adjustable numbers inside a model. Training's entire output.
Wilson intervalA confidence interval for a percentage that stays inside 0–100%, unlike the simpler method.
YAMLA human-friendly text format for settings files.
PART 22

Command cheat sheet

Everything you can do with this project, in the order you would normally do it. The reason the task runner exists (Part 10) is that these are the only commands you need to remember.

Getting started

# Get the code and install what it needs
git clone git@github.com:ziaur390/mlserve-ops.git
cd mlserve-ops
python tasks.py install

# Build the model: train it, export three runtimes, build the drift reference
python tasks.py pipeline

Everyday commands

CommandWhat it does
python tasks.pyList every available command with a description. Start here.
python tasks.py testRun all 255 checks (fast ones).
python tasks.py test-allRun everything, including checks that need Docker.
python tasks.py lintCheck code style and catch simple mistakes.
python tasks.py formatFix style problems automatically.
python tasks.py covRun checks and show which lines are not covered.

Working with the model

CommandWhat it does
python tasks.py trainTrain the model from scratch (~4 seconds).
python tasks.py exportProduce the three runtimes, and fail if they disagree.
python tasks.py referenceRebuild what "normal input" looks like, for drift detection.
python tasks.py pipelineAll three of the above, in order.
python tasks.py serveRun the API locally with auto-reload, for development.

Measuring

CommandWhat it does
python tasks.py benchRun the full benchmark. Writes results/raw.csv.
python tasks.py reportBuild the report and charts from that CSV.
MLSERVE_BENCH_CALLS=10 python tasks.py benchA quick run, for checking things work.

Operations

CommandWhat it does
python tasks.py driftRun drift detection once. Exit code 2 means "drift found" — a finding, not a failure.
python tasks.py seedInsert synthetic requests, so the backup drill has data.
python tasks.py backupCreate a dated archive with checksums.
python tasks.py restore-verifyRestore the newest archive and prove every row matches.
python tasks.py backup-listList existing archives.
python tasks.py smokeCheck the running stack actually answers on its endpoints.

The whole stack

CommandWhat it does
python tasks.py upStart all nine containers, built and in the right order.
python tasks.py logsFollow the logs from everything.
python tasks.py downStop everything, keeping the data.
python tasks.py nukeStop everything and delete the data. Destructive.

The one command that checks everything

# Style, tests, model build, benchmark, report, drift, backup, restore-verify
python tasks.py verify

# The same, plus the full container stack and a live smoke test (slow, needs Docker)
python tasks.py verify-all

One last thing

If you take a single habit away from this document, take this one:

When something works, ask what would make it fail. When something fails, ask why it was invisible. And when you cannot tell, say so — clearly, and with the reason.

That is what separates this project from a demo, and it is the whole difference between writing code that runs and building systems people can rely on.
