PART 6

The race with a stopwatch: benchmarking

Measuring how fast software runs sounds like the easiest job in computing. It is one of the hardest to do honestly. This part explains what the benchmark does, and every decision exists because a simpler version produced a wrong answer.

What is it?

A program that runs the model thousands of times in carefully controlled ways, records how long every single call took, and writes the results to a file so they can be analysed and re-checked.

48configurations tested
1,344timed calls per run
2different methods compared
3repeats of everything

Why did we need it?

The problem before it

You have three ways to run your model. You must pick one for production. Somebody will ask you why.

You could time one request of each on your laptop and pick the winner. But then: was your laptop busy? Was the first one penalised for warming up a cache? Was the difference real, or just one lucky run? Would it still be true tomorrow?

Without a real harness you have an opinion. With one you have evidence. And crucially, the evidence is checkable by someone else — which is the difference between a claim and a measurement.

How does it work here?

What gets measured

The benchmark runs every combination of these four things — 2 × 3 × 4 × 2 = 48 configurations:

SettingOptionsWhy it is a variable
Mode inproc, http Do we time just the model, or the whole round trip through the API? Both, because they answer different questions.
Runtime torchscript, onnx-fp32, onnx-int8 The main question: which is faster?
Batch size 1, 8, 32, 64 Does handling 64 at once beat handling them one at a time?
Concurrency 1, 4 Does sending several requests at the same time help, or just make everything slower?

Two ways of measuring, and why both are needed

Why we needed both modes

If you only measured inproc, you would know which engine is fastest but not what your customers experience. If you only measured http, a difference could come from the model or from the API layer — and you could not tell which.

Measuring both means a difference that appears in one mode but not the other can be attributed. That is the difference between "it is slower" and "the API layer is slower, the model is the same."

Reproducibility: the property everything else depends on

Five separate things are pinned so that a rerun is genuinely a rerun:

What is pinnedWhat it prevents
The random seedDifferent pictures being timed each run.
Per-configuration seeds from SHA-256Python's per-process random hashing, which silently made each run different. This was a real bug.

Warm-up: the easiest mistake to make

The very first time you run a model, the runtime does a lot of one-time setup: building internal graph structures, allocating memory, deciding how to schedule the work. The second call reuses all of it.

If you include that first call in your average, you are mostly measuring start-up cost and calling it speed. So the benchmark runs warm-up calls first and throws them away. It measures the steady state, which is what production actually experiences after the first request.

One call is one measurement, no matter how big

A subtle detail with a big effect. When a batch of 64 pictures is sent in one request, that counts as one latency measurement — not 64.

Imagine it like this

You order 64 pizzas in one phone call. The call takes 3 minutes. That does not mean each pizza took 3 minutes! If you counted it that way, ordering in bulk would look 64 times slower than ordering one at a time — which is the exact opposite of the truth.

What the benchmark refuses to do

One decision is worth calling out because it removes a result the project would otherwise be able to show.

While benchmarking, request logging is switched off. Saving each request to the database is slow, and because of how the web server works, those saves would show up in the next request's timing. The benchmark would then be measuring database write speed and reporting it as inference speed.

So logging is off — and the consequence is that the cost of logging is not measured anywhere in this project. That is stated plainly in the report rather than left as an unmentioned gap.

Where will you use this again?
  • Warm-up exclusion applies to any performance test: database connection pools, web servers, caches, compilers. Anything with one-time setup cost.
  • Separating layers — measuring the component versus the whole system — is how you find where time is actually going. It is the basis of all profiling.
  • Pinning thread counts and seeds is essential for any result you intend to compare, publish, or defend. It is also a standard part of designing scientific experiments.
  • Stating what you did not measure is a professional habit that builds trust far faster than claiming everything was covered.
PART 7

How to avoid fooling yourself: the statistics

This is the most important part of the document, and the one most projects skip. It contains the single most valuable lesson in the whole repository.

What is it?

A small set of mathematical tools that turn raw timings into statements you can defend — and that tell you when the data simply does not support a conclusion.

Why did we need it?

The problem before it

The benchmark produces 1,344 numbers. Some average is "faster" than another. Is that a real difference, or is it just the machine being slightly different from one moment to the next?

Here is the thing that makes this genuinely hard: there is no way to tell by looking at the numbers. A 15% speedup caused by a real improvement and a 15% speedup caused by your laptop's fan spinning up look identical in the output.

You need a way to measure your own measurement error. That is what this part is about.

The story of the flip

This is the moment the project changed direction, and it is worth telling properly.

We ran the benchmark twice. Identical command, identical machine, identical everything. And the results contradicted each other:

RunClaim about int8 at batch 8Direction
First runint8 is 1.47× slower than fp32one way
Second runint8 is 1.75× faster than fp32the opposite way

Same code, same model, same machine — and the answer completely reversed. Any conclusion drawn from either run alone would have been confidently wrong.

Why this happens

Look at the timings. In inproc mode a call takes between 0.03 and 0.7 milliseconds. That is about the time it takes to blink.

At that scale, ordinary background activity on your computer — a garbage collector pausing for a moment, the operating system switching tasks, a fan starting — is the same size as the difference being measured. You are trying to hear a whisper while someone is rustling paper.

The http measurements, by contrast, take 2–25 ms — far bigger than the rustling. Those stayed consistent between runs.

How does it work here?

Confidence intervals — giving every number an honest range

Instead of reporting "1.23× faster", every result is reported as a range: 1.23× [1.15, 1.31]. This says: the measurement came out at 1.23, and we are reasonably sure the true value lies between 1.15 and 1.31.

Two intervals are built differently, for a reason that matters:

TypeUsed forWhy it is done this way
Bootstrap Latency percentiles Latency is lopsided — a few very slow calls drag the average up. A symmetric range would put the lower bound somewhere impossible and understate the upper one. Resampling avoids assuming a shape.
Paired bootstrap Comparing two things The two measurements being compared came from the same machine at the same time — same temperature, same background load. Resampling them together preserves that. Comparing two separate intervals is a classic error that makes real differences look like noise.
Wilson interval Accuracy The model is 97.41% accurate. A naive interval would give a range like "96% to 101%", and a probability cannot exceed 100%. Wilson stays inside the possible range.
What "bootstrap" means, simply

You have 210 stopwatch readings. You want to know how much your average would wobble if you ran the experiment again.

You cannot run it again a thousand times. But you can do something clever: take your 210 readings and pick 210 at random from them, allowing repeats. Average those. Do that 2,000 times.

You now have 2,000 slightly different averages. Where most of them land is your confidence interval. You built a picture of your own uncertainty out of the data you already had — no extra runs needed.

The best idea in this project: measuring your own noise

Here is the clever bit that turns a confusing situation into an honest one.

The benchmark already runs every configuration three times. So for any one configuration — same runtime, same batch size, same everything — we have three independent measurements of the identical thing.

Any difference between those three repeats is, by definition, the harness measuring nothing at all. That is the noise floor. It is the answer to "how much difference can this setup produce out of thin air?"

The honest headline

The result this project is actually proudest of

The harness cannot resolve its own differences. The noise band is 0.58× to 1.71× — a range of nearly 3× — and every measured "speedup" sits inside it.

So the report flags 19 of 48 comparisons as "unresolvable" and says so directly, in bold, in the table.

Why this is a success and not a failure: because the alternative is a report that says "int8 is 1.57× faster!" and is wrong. Finding the limits of your own instrument is real engineering work. Pretending not to have limits is how bad decisions get made — and in this case the bad decision would be to switch production to int8 for a speed benefit that may not exist.

Knowing which percentiles are even measurable

There is a second, quieter honesty check. Percentiles need enough data to mean anything.

To report a p99 — the slowest one request in a hundred — you need at least 100 observations before a single one lands in that range. With only 3 observations in the tail, your "p99" is really just "the slowest one we happened to see", wearing a percentile's name.

PercentileObservations neededMeasurable in a quick run?
p50 (the middle)20Yes, easily
p90100Yes
p95200Sometimes
p991,000No — not in a quick run

So the report does not print a p99 and let you assume it is solid. It marks it as underpowered and tells you how far short you are — 20 calls short is very different from 20,000 calls short, and you deserve to know which.

Why we needed all of this

Because a benchmark's job is not to produce numbers. It is to produce numbers a stranger can act on safely. A number without its uncertainty is not actionable — it is a rumour with a decimal point.

And the moment you can measure your own error, you gain something unexpected: the ability to say "I don't know" with authority. That is a far more valuable professional skill than the ability to produce an impressive figure.

Where will you use this again?
  • Every performance claim you ever read. Ask: how many runs? what was the variance? is there a confidence interval? If not, it is marketing, not measurement.
  • A/B testing, load testing, database tuning, front-end optimisation — all the same problem, all the same tools. Latency is never normally distributed; bootstrapping is the standard modern answer.
  • The noise-floor idea generalises to any measurement instrument: run it on two identical things and see what it reports. A weighing scale that reads 100 g and 103 g for the same object cannot resolve a 2 g difference, no matter how precise it looks.
  • Wilson intervals for proportions are used for conversion rates, error rates, click-through rates — anywhere you are measuring a percentage near 0 or 100%.
  • The habit of reporting uncertainty will make you noticeably more credible than people who do not. It is rare, and it is obvious when you see it.
