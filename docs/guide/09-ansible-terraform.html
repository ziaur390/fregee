PART 14

The robot installer: Ansible

How you set up one server — or a hundred — without doing any of it by hand, and without forgetting step 7 next time.

What is it?

A tool that takes a written description of how a computer should be set up, and makes the computer match it. It connects over the network, checks what is already there, and only changes what is wrong.

Imagine it like this

You are moving into a new house. Instead of walking around deciding where things go, you write a checklist: "the kettle goes on the left counter, the plates in the top cupboard, the towels in the bathroom."

Now you hand that list to a helper. They set up the house. And the magic part: if you run the list again tomorrow, they check each item, see it is already correct, and change nothing. That is the whole idea.

Why did we need it?

The problem before it

Before the project can run, a server needs: the right user accounts, a firewall configured, the container engine installed, the code fetched, services installed with timers, log rotation set up. That is a long list of steps.

Done by hand, three problems appear immediately:

  • It is not repeatable. The second server will be set up slightly differently, because you will forget something or do steps in a different order.
  • It is not reviewable. Nobody can check your work. There is no record of what you did.
  • It is not recoverable. If a server dies, rebuilding it means doing everything again from memory.

How does it work here?

Six roles, each doing one job

RoleWhat it sets up
baseBasic system packages and settings that everything else assumes.
usersService accounts and their permissions.
firewallWhich network ports are open and which are closed. Deny by default.
dockerThe container engine itself.
deployThe application: fetch the code, install the timers and services that run it.
logrotateStops log files growing until the disk fills.

The word role just means "a reusable bundle of instructions that belongs together." It means you can apply the firewall rules to any server, not only this one — the same bundle works for a different project entirely.

The key idea: describe the destination, not the journey

Why "changed: 0" is the goal

When you run the setup a second time on an already-correct machine, the ideal output is changed: 0, failed: 0 — meaning "everything was already exactly right, I did nothing."

This is not a technicality. It is a real test of whether the description is complete and correct. If running it twice changes things, the description does not fully determine the outcome — which means two servers set up from it could end up different. Idempotent is the formal word, and it is the property that makes automation trustworthy.

What we proved, and what we could not

CheckResult
The configuration is syntactically validProven — passes
All 56 tasks in 6 roles resolve correctlyProven — listed and verified
Best-practice linter finds no problemsProven — clean
Actually setting up a real, live machineNot proven here

The last row is the honest gap. Testing the real thing requires a virtual machine, which on this Windows machine requires a system component that is not currently enabled. It is not a flaw in the configuration — it is simply not exercised.

So the project says exactly that: "the configuration is verified to be well-formed and complete; it has not been applied to a real machine." It would be easy to phrase that as "fully verified Ansible deployment" and most readers would not check. Stating the limit is the entire point of the project.

A real problem we hit — and its lesson

Two versions of the linter disagreed

The automated build machine used one version of the quality-checking tool; the local machine had an older one. They gave different answers about the same files.

This is a genuinely nasty class of problem: the check passes for you and fails for everyone else, with no code difference to explain it. It wastes hours, and it erodes trust in the automation.

The fix has two parts. First, run the newer version locally to make the two agree. Second, understand why the newer version complained — in this case, it wanted variable names to be more specific, so that a variable belonging to one role does not accidentally collide with a similarly-named variable in another role. That is a real robustness improvement, not nitpicking.

The lesson: pin your tool versions, and when a check disagrees between two environments, treat that as a genuine finding rather than an annoyance to silence.

Where will you use this again?
  • Ansible is one of the three big configuration tools (with Puppet and Chef) and is the most common in cloud and DevOps roles. Knowing roles, idempotency and inventory is directly marketable.
  • Idempotency as a concept applies far beyond servers: database migrations you can re-run, deployment scripts, API operations, message processing. It is one of the most valuable ideas in distributed systems.
  • Configuration as code — storing your infrastructure setup in version control, where it can be reviewed and rolled back — is standard practice everywhere.
  • Being explicit about untested paths will come up every time you ship automation. "I verified the script parses but did not run it against production" is a complete, honest sentence that colleagues can act on.
PART 15

The robot builder: Terraform

Ansible sets up a computer that already exists. Terraform creates the computer in the first place. Together they cover the whole life of a server.

What is it?

A tool where you write down what computers you want, and it talks to your cloud provider to make them exist — networks, servers, addresses, firewalls and all.

Imagine it like this

Ansible is the helper who furnishes your house. Terraform is the builder who builds the house — and who will also knock it down cleanly when you are done with it.

Why did we need it?

The problem before it

You need a server. So you log into a cloud website, click through a form, choose a size, pick a region, click create. It works. Now do it again for the next environment.

Two problems. First, nobody wrote down what you clicked — there is no record, no review, no way to make the same thing again exactly. Second, when you are finished experimenting, the server keeps running and keeps costing money, because nothing told the cloud to stop.

How does it work here?

The same description, two destinations

The infrastructure is written once as a reusable module, then used by two different environments:

EnvironmentCreatesPurpose
local A virtual machine on your own computer A place to practise and test without paying anything or touching the internet.
free-tier A real cloud server on a free allowance Proves the same description works against a real provider.

This is the point of writing infrastructure as code: the same description produces the same shaped thing in both places. Testing locally tells you something about what will happen in the cloud.

The clever part: a server that sets itself up

Creating a server and then configuring it are two separate steps. But there is a neat trick that merges them: when the server is created, you hand it a script to run the moment it first boots.

What we proved, and how

CheckResult
The provider plugin downloads correctlyProven
The description is valid — for both environmentsProven
Terraform can plan the change without doing itProven — "2 to add, 0 to change, 0 to destroy"
Formatting follows the standard styleProven
The plugin version is locked downProven — lock files committed
Two ideas worth stealing

Plan before applying. Terraform can tell you exactly what it is about to do, without doing it: "2 things will be created, 0 changed, 0 destroyed." That is a safety net no manual process has. You get to read the consequences before you accept them.

Lock the plugin version. The tool relies on an add-on written by someone else. If that add-on publishes a new version with a bug, your infrastructure breaks for reasons that have nothing to do with your code. Committing a lock file means you only move versions when you choose to. This is the same lesson as the Ansible version mismatch — pin your dependencies — showing up in a different place.

Where will you use this again?
  • Terraform is the most widely used infrastructure-as-code tool and appears in nearly every cloud job advertisement. It works with AWS, Azure, Google Cloud and dozens of others.
  • The plan/apply pattern — preview the change, then confirm it — is the correct way to make any risky change.
  • Self-provisioning machines are how auto-scaling works. When load rises, new servers appear and must configure themselves with nobody watching.
  • Being able to destroy cleanly is a genuine engineering concern: orphaned cloud resources are a common and expensive problem in real companies.
  • Lock files appear in every ecosystem — package-lock.json, poetry.lock, Gemfile.lock. The reason is always the same.
