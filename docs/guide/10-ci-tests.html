PART 16

The homework checker: CI/CD

Robots that check your work every time you change it — so that problems are found in minutes, by a machine, instead of in production, by a customer.

What is it?

Continuous Integration means: every time you save your work to the shared repository, a robot automatically checks it. Continuous Delivery means: if all the checks pass, the robot can also publish or deploy it.

Imagine it like this

You hand in homework. Instead of waiting a week to find out you got question 4 wrong, a helper checks it the moment you finish, every time, and tells you immediately.

An hour later you have already forgotten what you were thinking when you made the mistake. A week later you have no idea at all. Checking immediately is worth ten times more than checking eventually.

Why did we need it?

The problem before it

Your checks only run when you remember to run them. And you will forget — not through carelessness, but because at 1am when you are fixing one last thing, running the full test suite is the step that feels skippable.

Then it becomes someone else's problem. Broken code reaches the shared branch, and everyone who pulls it gets a broken project. The person who finds out is never the person who broke it.

How does it work here?

Three separate robot jobs

Why the benchmark runs on a tag, not on every change

The full benchmark takes several minutes and produces a report with charts. Running it on every single save would be wasteful and would produce dozens of near-identical reports nobody reads.

So it runs when you mark a version — a tag like v0.1.0, meaning "this is a real release." The report and the charts get attached to that release permanently, as the record of what that version measured on the day it was published.

Why this project avoids paid services entirely

The rule for this project is zero cost. So there is no paid monitoring service, no paid build runner, no managed database. Everything runs on free allowances or on the developer's own machine.

This is not only about money. It is also a stronger demonstration: an engineer who can build a complete, monitored, tested, deployable system with free tools has shown they understand what each piece is really for. Anyone can buy a service. Knowing which service you would buy, and why, requires the understanding this project is trying to build.

The robot that updates dependencies

There is a fourth robot that does something different: it watches for new versions of the tools the project uses, and proposes an update for each one.

Robot proposes an update toWhy
The actions used in the checking itselfKeeps the checking machinery current and secure.
Python librariesSecurity fixes and bug fixes in dependencies.
The base container imageOperating-system security patches.

Each proposal arrives as a small, separate change you can review and accept or reject. That is much safer than updating everything at once, because if something breaks you know exactly which change caused it.

Why not accept them all automatically?

Because updates can genuinely break things, and the project's own history proves it. When the base image moved from Python 3.12 to 3.14, the automatic checks all passed — but they had been testing Python up to 3.13 only. The version actually being deployed was never tested.

Everything was green. The gap was invisible. This is the most dangerous kind of problem: a check that passes for the wrong reason.

The fix was not to stop accepting updates. It was to add a check that reads the container's stated Python version and refuses to pass unless that version is in the tested list. Now the two cannot drift apart silently again — in either direction.

Where will you use this again?
  • CI is universal. GitHub Actions, GitLab CI, Jenkins, CircleCI, Azure Pipelines — every professional team has one, and every interview will touch it.
  • Splitting checks into "correct", "secure" and "performance" mirrors how real teams organise their pipelines, and how they think about release readiness.
  • Automated dependency updates are now standard practice and a genuine security control. Most breaches exploit known vulnerabilities in outdated dependencies.
  • "A check that passes for the wrong reason" is a phrase worth remembering. When something is green, ask what it would take for it to go red. If you cannot answer, it may be checking nothing.
PART 17

How we know it works: the tests

255 automatic checks. This part explains what they are for, and why the most valuable ones are the ones that check for failure.

What is it?

Small programs that run your code and check it behaves as expected. Run them all with one command; if anything is wrong, you are told immediately.

Why did we need it?

The problem before it

Software changes constantly. Every change risks breaking something that used to work — and the connection is often not obvious. You fix a display bug and break the backup job.

Tests are how you make changes confidently. Without them every change is a gamble, and the natural response is to become afraid of changing anything. That is how projects die: not from bugs, but from nobody daring to touch them.

The most valuable kind of test: checking that things fail correctly

Most tests check that things work. The best tests check that things fail properly — because failure paths are rarely exercised by hand and are where the surprising bugs live.

TestWhat it proves

Why the "no drift" test is as important as the "drift" test

It would be easy to write a drift detector that always shouts "DRIFT!" and pass every test that checks it detects drift. It would also be completely useless.

So the tests check both directions: it must fire on genuinely shifted data, and stay quiet on normal data. A detector that fails either one is not usable. Testing only the positive case is one of the most common mistakes in test suites.

One test worth explaining in detail

During the work on this project, the report took 113 seconds to generate because of how the statistics were calculated, and it was made about 10× faster. Whenever you speed something up, you must prove the answer did not change — and "close enough" is not good enough for a replacement that is supposed to be identical.

So there is a test that runs both the old way and the new way on exactly the same random draws, and asserts the results match exactly. Not "approximately." Exactly.

That distinction matters. If the test only checked that the answers were close, a genuine difference could hide inside the randomness and nobody would ever know. Pinning the random draws removes the randomness from the comparison entirely, leaving only the thing being tested.

Where will you use this again?
  • Testing failure paths is the single most underrated testing habit. It is where the interesting bugs are, and it is what separates a test suite that gives confidence from one that gives the feeling of confidence.
  • Testing both directions — detects when it should, stays quiet when it should — applies to every detector you ever build: alerts, filters, validators, search functions, anomaly detection.
  • Proving an optimisation did not change the result is how you safely make anything faster. It is also exactly what the export parity check does for the three runtimes.
  • Pin the randomness in any comparison involving chance, or you are comparing noise to noise.
